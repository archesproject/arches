# Hooks

Hook scripts customize the container lifecycle at specific points, without needing to fork
or edit `arches-docker` itself. There are two kinds: a required **build-time** hook baked
into the Docker image, and optional **runtime** hooks sourced by the entrypoint.

---

## Build-time hooks

### `build_deps.sh` (required)

Runs during `docker build`, as **root**, in **both** stages of
`production/Dockerfile.alpine` — it is `COPY`'d into the image and executed directly, before
any application dependencies are installed. Unlike every hook below, it does **not** have the
virtualenv activated, `APP_ROOT` is not set, and there is no database or Elasticsearch
available.

Use this to install OS-level packages your project needs that aren't already in the base
image (e.g. `poppler-utils`, extra fonts, a GIS library).

`BUILD_STAGE` tells you which stage is running:

- `build` — compiles C extensions and builds frontend assets. Install `-dev`/header packages
  and build toolchains here.
- `deploy` — the final, minimal runtime image. Install only the runtime shared
  libraries/binaries actually needed at runtime.

```bash
#!/bin/bash
case "${BUILD_STAGE}" in
    build)
        apk add --no-cache some-package-dev
        ;;
    deploy)
        apk add --no-cache some-package
        ;;
esac
```

**This file must always exist and stay committed to the project repo** — the Dockerfile
copies it by exact path, so a missing file fails the build. `init-project.sh` generates a
no-op stub; `make build` and the CI build workflow will also recreate it if it's ever
missing, but never overwrite a customized one. Because it's copied by name, editing it
invalidates the `pip install`/`npm i` layers below it in the build cache — unrelated changes
to the other hooks in this directory do not.

## Runtime hooks

Runtime hook scripts are sourced by the entrypoint at specific points in the app lifecycle.
Place `.sh` files here named after the hook you want to implement.

All runtime hooks run with the virtualenv already activated and `APP_ROOT` as the working
directory.

### `pre_dev.sh`

Runs before the Django development server starts (`run_dev_server`).

Use this to install editable sibling packages, set up local tooling, or any other
dev-only setup that should happen each time the container starts.

The default `pre_dev.sh` generated by `init-project.sh` scans `${WEB_ROOT}` for mounted
sibling packages and installs them in editable mode, uninstalling any regular (non-editable)
copy first to prevent stale site-packages from shadowing the editable install:

```bash
for toml in ${WEB_ROOT}/*/pyproject.toml; do
    pkg_dir=$(dirname "$toml")
    [ "$pkg_dir" = "${APP_ROOT}" ] && continue
    echo "Installing editable: $(basename $pkg_dir)"
    cd "$pkg_dir"
    pkg_name=$(python3 -c "import tomllib; d=tomllib.load(open('pyproject.toml','rb')); print(d.get('project',{}).get('name',''))" 2>/dev/null)
    if [ -n "$pkg_name" ]; then
        pip uninstall -y "$pkg_name" 2>/dev/null || true
    fi
    pip install --no-deps -e .
done
```

Add project-specific setup (management commands, etc.) after the loop.

---

### `pre_test.sh`

Runs before the test suite (`run_tests` / `run_tests_watch`), before the very first run in
the watch case — not on every re-run.

The built-in `pre_test.sh` just sources the built-in `pre_dev.sh` above, so mounted sibling
packages get the same editable install for test runs that they get for the dev server.

To override: place your own `pre_test.sh` in `.runtime/hooks/`. It replaces the built-in hook
entirely — it does not also run `pre_dev.sh` unless your override sources it itself:

```bash
#!/bin/bash
source "${APP_ROOT}/.runtime/internal/hooks/pre_dev.sh"
python manage.py my_test_fixture_setup
```

---

### `pre_start.sh`

Runs before the Gunicorn production server starts (`run_gunicorn`).

Use this for production startup tasks: running migrations, collecting static files,
warming caches, etc.

Example:

```bash
#!/bin/bash
python manage.py migrate --no-input
python manage.py collectstatic --no-input
```

---

### `demo_mode.sh`

Runs in `run_server` when `ARCHES_DEMO_MODE=true`, after `pre_start`. A built-in default
lives in `.runtime/internal/hooks/demo_mode.sh` and restricts access for public demo
deployments: it reads a comma-separated list of nginx location paths from the
`ARCHES_DEMO_RESTRICTED_PATHS_ID` SSM parameter and redirects each to `/auth/`, injecting the
rules directly into the running nginx config.

To override this hook entirely, place your own `demo_mode.sh` in `.runtime/hooks/`.

---

### `post_demo_user_setup`

Runs at the end of demo user provisioning (creation/update of the `demo-user` account and
its group memberships), inside `run_server`'s demo setup path.

Use this for any additional demo-account setup — assigning extra permissions, seeding
demo-specific data, etc.

---

### `post_load.sh`

Runs after `manage.py packages -o load_package` completes during `reset_database`.

Use this to load additional fixtures, import data, or run any setup that depends on
the package being loaded.

Example:

```bash
#!/bin/bash
python manage.py loaddata my_fixtures.json
```

---

### `post_reindex.sh`

Runs after `manage.py es reindex_database` completes during `reset_database`.

Use this for any final setup steps that require a fully initialized database and
search index.

Example:

```bash
#!/bin/bash
python manage.py create_admin_user
```
