## Arches 8.2.0 Release Notes

### New Features

- Confirm support for Django 6.0 [#12584](https://github.com/archesproject/arches/pull/12584)
- Enable dynamic importing of TypeScript files [#12601](https://github.com/archesproject/arches/pull/12601)
- Move packages in arches-dev-dependencies repo into local peerDependencies [#12663](https://github.com/archesproject/arches/pull/12663)
- Move default configs from cards_x_nodes_x_widgets to node config [#12725](https://github.com/archesproject/arches/pull/12725)
- Add `--use_multiprocessing` (-mp) and `--max_subprocesses` (-mxp) options to the `etl` management command to control indexing parallelism, matching the `es` command [#PR](https://github.com/archesproject/arches/pull/PR)
- Extract sidenav into its own template for project-level customization [#12689](https://github.com/archesproject/arches/issues/12689)
- Datatypes can define their own copy logic when a resource or tile are cloned [#12706](https://github.com/archesproject/arches/pull/12706)
- During resource cloning, distinct resource_x_resource records are created for resource instance (list) nodes [#12715](https://github.com/archesproject/arches/pull/12715)
- Re-enable resource cloning in the resource editor and add copy-specify logic for edit-log display [#12749](https://github.com/archesproject/arches/pull/12749)
- Upgraded rdflib to 7.6.0 and Python 3.14 is now supported [#12790](https://github.com/archesproject/arches/pull/12790)
- Add command to calculate descriptors independent of ES index [#12828](https://github.com/archesproject/arches/issues/12828)
- Add multi-card descriptor [#12829](https://github.com/archesproject/arches/pull/12829)
- Package migrations: version an Arches application's graphs and tile data the way Django migrations version schema, with `makepkgmigrations`, `migratepkg` and `showpkgmigrations` [#9054](https://github.com/archesproject/arches/issues/9054)

### Breaking changes

- The minimum supported version of Python is now 3.12.

- The `v3` migration management command is removed.

- Package migrations are rebuilt on Django's own migration machinery. Migration files now live in
  `<app>/migrations/package_migrations/`, applied state is recorded in the `arches_package_migrations`
  table, and operations are imported from `arches.db.package_migrations.operations`. Any package
  migration written against the previous implementation must be regenerated; the previous
  `arches.db.migration_operations` classes and the `package_migrations` table are removed [#9054](https://github.com/archesproject/arches/issues/9054)


### Upgrading Arches

1. You must be upgraded to at least version 8.1.0 before proceeding. 

2. Upgrade to Arches 8.2.0
    ```
    pip install --upgrade arches==8.2.0
    ```

### Upgrading an Arches project

1. In pyproject.toml, make these updates:
    - Update `requires-python` to `">=3.12"`
    - Remove `"Programming Language :: Python :: 3.11"`
    - Remove `"Framework :: Django :: 5.2"`
    - Add `"Programming Language :: Python :: 3.14"`
    - Add `"Framework :: Django :: 6.0"`

1. Apply automatic updates:

    ```
    python manage.py updateproject
    ```

1. In package.json:

    Remove "arches-dev-dependencies" from "devDependencies" and run:


        ```bash
        rm -r node_modules; rm package-lock.json
        npm install
        ```

1. Migrate database:

    ```bash
    python manage.py migrate
    ```

1. If you maintain an Arches application that ships graphs, adopt package migrations for it:

    Export each graph into the application, then generate its first migration.
    Resource models belong in `pkg/graphs/resource_models/` and branches in `pkg/graphs/branches/`;
    `load_package` reads only those two directories.

    ```bash
    python manage.py packages -o export_graphs \
        -d <app_dir>/pkg/graphs/resource_models -g <graphid>
    python manage.py makepkgmigrations <app_label>
    ```

    The first generated migration describes the whole graph, because no migration history exists
    yet to diff against.

1. Record package migrations on databases that already have the graphs:

    A site that installed a package with `packages -o load_package` already has its graphs, so the
    first migration must be recorded rather than run — applying it would try to create rows that
    already exist. Once per Arches application:

    ```bash
    python manage.py migratepkg <app_label> --fake
    ```

    Confirm the result, then apply subsequent migrations normally with `migratepkg`:

    ```bash
    python manage.py showpkgmigrations <app_label>
    ```

    New installs do not need this step: `load_package` and the migration history describe the same
    state, so there is nothing to reconcile.

1. Plan a maintenance window before running `migratepkg` on a large database:

    A package migration is generated as two files: a graph migration that rewrites the graph
    definition and republishes it, and a data migration that brings existing tiles in line and then
    moves resources onto the new publication. Between the two, resources are still on the previous
    publication, so **the resource editor shows them read-only until the data migration finishes**.
    On a database with millions of tiles that window is the length of the backfill.

    The data migration runs outside a transaction and selects work by tile content, so it can be
    interrupted and re-run: already-migrated tiles are skipped. Batch size is written into the
    generated file and can be edited before running.

    `migratepkg` does **not** reindex. Reindex affected resources afterwards, or search results will
    reflect the old graph:

    ```bash
    python manage.py es reindex_database
    ```

1. Validate your graphs verify all default values are valid:

    ```bash
    python manage.py validate --verbosity=2
    ```
